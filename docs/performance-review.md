# 性能复审（2026-10-11）

本轮审查以第三轮优化后的代码为基准，重点是用户操作的完整成本。原有规模基准中的 `fts_search` 只测 `ArchiveStore::query_messages`，不包含搜索接口的结果定位、目录查询及 HTTP 响应构造。原有搜索词每 10,000 条消息才出现一次，不能代表常见词搜索。

新增诊断程序：[`query-performance-review.rs`](../crates/archive-store/examples/query-performance-review.rs)。使用项目当前的 SQLite 和现有依赖，构建与运行全部离线；实验索引仅添加到本进程生成的合成数据库。业务代码、依赖与锁文件未在本轮修改。

## 1. P1：减少搜索结果的提前定位

代码：[`archive.rs`](../apps/server/src/api/archive.rs)、[`messages.rs`](../crates/archive-store/src/query/messages.rs)、[`App.tsx`](../src/App.tsx)。

`search_messages` 对每条结果调用 `message_offset_in_conversation`，通过范围 `count(*)` 算出其会话内位置；前端默认取 50 条。计数已经能使用会话时间索引，但仍需遍历目标之前的记录。相同大群的多条命中会重复计算这些范围。

百万合成消息、其中 50 万条属于同一大群的定向测量中，仅 50 条结果的定位就达到秒级；这部分成本完全没有包含在原 `fts_search` 指标中。

建议点击结果后只定位选中的一条。兼容原接口的定位字段，增加可选的轻量搜索模式或独立响应，不能用虚假的 `offset_in_conversation = 0` 代替真实位置。会话名称也可按会话缓存，避免同一请求内重复查找。之后再考虑通过消息锚点直接加载上下文，减少对绝对页码的依赖。

验收应测真实搜索 API 的首次/P50/P95，包括升降序、多个结果属于同一大群，以及点击后定位。保留同时间下的稳定 ID 排序与旧投影语义。

## 2. P1：大群消息总数复用已有派生统计

代码：[`App.tsx`](../src/App.tsx)、[`messages.rs`](../crates/archive-store/src/query/messages.rs)、[`derived.rs`](../crates/archive-store/src/derived.rs)。

前端每次翻页、改变每页条数或排序都同时请求消息与总数。当前 `count_messages` 即便只有 `conversation_id` 条件，也执行原表 `count(*)`；第三轮已有准确的 `archive_conversation_stats.message_count`，但此路径尚未利用它。

建议仅对无其他筛选的会话计数使用派生表；没有派生表的旧只读归档继续原查询，有关键词、发送人、时间、类型或附件条件时仍按实际筛选统计。前端可按认证会话、会话 ID 与归档 revision 复用计数，避免翻页和反向排序重新发相同请求。归档更新时必须失效。

这一项复用已有数据结构，无需新增维护触发器，比继续增加写入索引更适合优先实施。

## 3. P2：顺序翻页增加游标路径，保留任意页码跳转

代码：[`messages.rs`](../crates/archive-store/src/query/messages.rs)。

当前分页已避免读取被跳过消息的正文，但 `OFFSET` 仍逐项遍历索引。原百万规模基准全局深页 P50 为 151.10 ms；定向诊断也证实记录键读取随偏移增长。

建议上一页/下一页使用 `(sent_at, stable_message_id)` 游标，原页码查询继续兼容。诊断验证了相同时间下游标与 OFFSET 返回的 100 个 ID 完全相同。游标实验只测记录键，且假定调用方已有锚点，不包含通过 OFFSET 查找锚点的成本，不能把实验比值直接作为完整请求加速倍数。

游标必须使用存储投影排序键，不能直接拿旧修订正文中的时间代替；每个排序方向分别维护锚点，归档 revision 更新后清除页锚点。随机跳到一个从未访问的页码仍需要 OFFSET 或其他定位机制。

## 4. P1：搜索区分稀有词、高频词和附件名

代码：[`messages.rs`](../crates/archive-store/src/query/messages.rs)。

搜索先将全文与附件名的全局候选 ID 做 UNION，再读取消息、排序和限制结果数。稀有词适合这条路径；常见词会产生很大的候选集合，`limit = 50` 不会限制构造候选集合的工作量。

新增诊断中，全部消息都含有的常见词在只返回 50 条时 P50 为 6.01 s。这项测量发生在添加实验反向索引之后，不能当作未添加该索引的精确基线；它验证了单靠该索引仍不能解决高频词延迟。正式实施前还需补齐原索引下的高频词对照及真实搜索 API 测量。

附件分支使用 `LIKE '%关键词%'`，原查询计划先扫描 `message_media`，为每个引用查询 `media` 的名称。普通文件名 B-tree 无法直接解决包含式匹配。单独增加反向索引不保证改变连接顺序：定向实验里完整稀有词搜索没有明显提速，孤立附件子查询还出现回退。

建议先补齐高频词、零命中词、文件名命中及共享附件密集场景的基准。对附件分支比较“先检查 media 名称、再通过反向索引解析引用”的计划，索引与查询方式一起验收，并计入导入时间与数据库大小。高频词可进一步比较时间索引驱动、FTS 行号验证的限量路径；稀有词保留候选驱动。不能为了 LIMIT 提前丢弃候选，或改变包含匹配、组合筛选、去重及排序语义。

## 5. P2：导出减少准备阶段，并避免跨会话重复搜索

代码：[`export.rs`](../apps/server/src/service/export.rs)、[`messages.rs`](../crates/archive-store/src/query/messages.rs)。

`ArchiveExportSource::new` 在准备元数据时读取并完整反序列化所有选中消息，正式导出再逐会话读取并解析一次。第三轮百万基准准备耗时 9.34 s，JSON 总计 38.30 s，准备约占 24%。

若导出带关键词，正式输出每个会话都重新调用同一套全局搜索候选查询。候选在一条 SQL 内复用，但不会自动跨不同会话 SQL 复用；常见词命中很多会话时，工作量可能随会话数放大。原完整导出基准没有关键词，没有覆盖这个场景；本轮未测量其完整导出耗时。

建议先测带筛选的多会话导出，再比较同一快照内复用筛选结果、轻量元数据聚合或一次有序遍历的方案。复用候选要控制内存，避免将百万 ID 或全部消息长期留在内存中。快速路径需保留旧修订投影兼容、纳秒/闰秒排序、简化模式隐藏公告，以及脱敏的上下文。

会话统计中的 `media_count` 是去重附件数，导出的计数是消息附件引用数，不能直接互换。原子发布、取消清理、快照一致性和不覆盖已有文件也必须继续保持。

## 6. P2：首次导入先分阶段剖析，再压缩热路径

代码：[`revision.rs`](../crates/archive-store/src/revision.rs)、[`derived.rs`](../crates/archive-store/src/derived.rs)、[`ingest.rs`](../crates/archive-store/src/ingest.rs)。

第三轮百万首次写入由 359.95 s 增至 384.22 s，10 万和 50 万也有回退。新增派生结构有写入代价，但现有单次基准不足以把每一部分成本精确归因。

可确认的逐条工作包括：FTS 修复预检、消息内容克隆及两份序列化、既有消息查找、FTS/映射写入和统计触发器。重叠批次还可能反序列化旧正文，再分别克隆、序列化和计算两个 canonical hash。

建议增加这些阶段的累计计时，优先比较将修复预检与既有消息查找合并、按需生成正文 JSON、同 ID/同哈希快速判断，以及保持字节结果一致的序列化哈希。旧版本写入后的每批最多一次修复扫描仍需保留，不能为了提速跳过失效映射修复。

首轮先验证较小的可重复批次，再复测百万吞吐。保持原内容哈希、跨采集器去重、修订记录、回滚和旧投影行为；不得通过改变哈希算法、移除一致性触发器或降低事务持久性来宣称优化。

## 实施顺序与复现

先做搜索按需定位与无筛选计数，并补齐高频词搜索对照，再做游标浏览；之后处理筛选导出和首次导入热路径。前面的项目直接针对交互延迟，后面几项先补足测量再决定实现，不建议继续泛化增加索引或缓存容量。

最终定向报告：[`1000000.json`](../target/benchmarks/query-review-report-69f750bf8bde47faa355f5298384f475/1000000.json)。程序使用 Release 构建，SQLite 版本以该报告为准。下表都是本轮定向诊断的预热 P50，不是生产 SLA。

| 定向指标 | 当前路径 | 对照/实验路径 | 测量范围 |
| --- | --- | --- | --- |
| 50 条搜索结果定位，升序/降序 | 1,607.47 / 1,967.12 ms | 点击后定位尚未实现 | 只计会话位置计算 |
| 大群无筛选总数 | 94.78 ms | 派生统计 0.0266 ms | 50 万条消息的单个会话 |
| 全局 80% 位置读取 100 个记录键 | OFFSET 93.41 ms | 已知游标 0.0479 ms | 不含正文和锚点查找 |
| 原附件候选查询 | 44.42 ms | media 先过滤 + 反向索引 11.17 ms | 文件名零命中；孤立 SQL 分支 |
| 仅增加反向索引后的附件候选查询 | 522.66 ms | — | 孤立 SQL 分支；显示计划回退风险 |
| 稀有词完整消息页查询，增加反向索引前/后 | 68.23 / 55.67 ms | — | 含正文解析；单次运行对照不代表稳定加速 |
| 常见词消息页查询 | 6,008.62 ms | — | 已有实验反向索引，返回 50 条 |

原附件计划为 `SCAN mm` 后逐引用查 media；仅加索引后仍为 `SCAN mm USING COVERING INDEX review_media_reverse`。media 先过滤的实验计划为 `SCAN media_search` 后通过反向索引 `SEARCH mm (media_id=?)`。不能用孤立分支的回退推导完整搜索一定同幅变慢，也不能用孤立分支提速推导完整请求同幅提速。

诊断断言验证了升降序位置与合成数据的预期一致、游标与 OFFSET 的 100 个 ID 相同、两种附件连接方式的全部命中 ID 集合相同，以及稀有词最终计数正确。它们不替代将来业务修改的组合筛选、共享附件及接口兼容测试。

运行定向诊断：

```powershell
& "$env:USERPROFILE/.cargo/bin/cargo.exe" run --release --locked --offline `
  -p archive-store --example query-performance-review -- 1000000
```

诊断使用 100 万条合成消息、约 1,001 个会话、50 万条大群消息、5 万个附件引用，记录 5 次预热后的样本与查询计划。数据通过 SQL 生成，未走生产 ingest；正文内不包含附件元数据，附件关联用于测量搜索 SQL。结果不能作为首次导入、导出或完整 HTTP 延迟的基准，也不直接与原生产 API 基准作加速比对。原始报告保存在被 Git 忽略的 `target/benchmarks/`。
