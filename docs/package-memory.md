# 大包内存分配基准

基准仅生成确定性的消息、附件和密文字节，不发现企业微信源目录，不访问网络，不使用真实密钥。程序比较原有分配策略与当前生产 API；原有策略保留在基准程序内，并非历史二进制的完整进程对照。

## 运行

已有 Rust 工具链和依赖缓存时，在仓库根目录使用 PowerShell：

```powershell
$env:RUSTUP_AUTO_INSTALL = '0'
$env:CARGO_NET_OFFLINE = 'true'
& "$env:USERPROFILE/.cargo/bin/cargo.exe" build --release --locked --offline -p archive-transfer --example package-memory
foreach ($mode in @('json-legacy', 'json-current', 'encode-legacy', 'encode-current', 'decode-legacy', 'decode-current')) {
    & './target/release/examples/package-memory.exe' $mode 16
}
```

最后一个参数是合成附件的 MiB 数，范围为 1 至 128，默认 16。每种模式使用独立进程；输出仅包含模式、字节数、摘要、耗时与内存计数。临时夹具由当前进程创建并自动清理，失败时仅报告稳定错误名。所有依赖沿用锁文件，不下载或安装工具。

## 测量范围

| 模式 | 比较内容 |
| --- | --- |
| JSON 导入 | 原有整份 `Value` 解析、契约转换及完整序列化校验缓冲，与直接契约解析和流式摘要比较。输入为含单个内嵌附件的合法完整 JSON。 |
| 包编码 | 已准备好契约和密文字节之后，原有额外明文序列化、十六进制字符串及最终包缓冲，与流式摘要、按块格式化和精确预留输出比较。 |
| 密文字段解码 | 原有文件缓冲、十六进制字符串、验证时临时解码和调用方再次解码，与借用输入字符串、一次解码及精确分配比较。 |

程序用 `System` 外的计数分配器记录 Rust 请求分配的存活字节数。构建夹具后重置阶段峰值，排除夹具构建的暂时分配；编码阶段保留的契约和密文输入计入峰值，导入阶段不保留夹具对象。输出同时记录输入基线、阶段峰值和相对基线的增量。

这不是 Windows 工作集、RSS 或进程全部内存；不包含分配器管理开销、底层 realloc 可能发生的暂时复制、CNG 内部内存和 WebView。包编码与解码夹具使用合成密文，不测 RSA/AES 本身，不代表完整采集、加解密或 HTTP 导入的端到端内存。每组前后输出长度和摘要应相同；消息关系、旧时间格式、校验失败、GCM 完整性及临时文件清理另由回归测试覆盖。

## 合成对照结果

2026-11-06 在 Windows x64 使用仓库 Release 配置运行，每个规模、每种模式各启动三个独立进程，未与编译或测试并行。下面记录三次中最大的阶段堆峰值，包含编码阶段已存在的输入；单位为 MiB。原始报告位于忽略的 `target/benchmarks/package-memory-1320b6b094614de6a05cf900184924d3/report.json`，另含各次耗时、输入基线、阶段增量和构建 EXE 哈希。

| 合成附件 | 路径 | 原有分配策略 | 当前 API | 峰值减少 |
| --- | --- | --- | --- | --- |
| 16 MiB | JSON 导入 | 96.01 | 64.01 | 约 33% |
| 16 MiB | 包编码 | 320.02 | 128.01 | 约 60% |
| 16 MiB | 密文字段解码 | 192.01 | 96.01 | 约 50% |
| 32 MiB | JSON 导入 | 192.01 | 128.01 | 约 33% |
| 32 MiB | 包编码 | 640.02 | 256.01 | 约 60% |
| 32 MiB | 密文字段解码 | 384.01 | 192.01 | 约 50% |

16 MiB 附件对应约 32 MiB 契约 JSON 和 64 MiB 加密包编码；32 MiB 附件对应约 64 MiB JSON 和 128 MiB 包编码。所有规模、模式及重复样本的对应输出长度和 SHA-256 均一致。耗时受进程启动、文件缓存、后台负载和 CPU 状态影响，不据三次样本宣称稳定吞吐提升。内存结果也不代表完整工作台或真实加解密进程的峰值。

## 实现与边界

- JSON 导入直接构造 `ClientExportV1`，跳过额外阅读视图；原有时间字段的递归归一化仍覆盖 `raw_payload`。校验仍在归档写入前完成。
- 摘要使用原 serde 序列化次序和字节，不再保留完整序列化副本。包编码保持与原 `EnterprisePackageV1` 完全相同的 JSON 字节。
- 密文文件缓冲只保留到解析结束，未转义的十六进制字段直接借用输入，解码只分配实际所需长度。试验中过大的 reader scratch 会抵消减少副本的收益，因此此路径使用 slice 解析；JSON 导入仍使用缓冲 reader。
- 附件按最多 64 KiB 二进制块解码、哈希和写入；全部验证成功后才原子发布。写入失败或校验失败只清理当前任务拥有的 `.partial`。已有附件也必须校验传入内容。归档阶段逐附件、逐批次释放内存。
- 采集端通过不可变共享引用读取缓存，按需复制脱敏，生成密文后先释放明文，再编码加密包。

完整密文、完整明文和契约对象仍存在随单包大小增长的阶段；单个 JSON 字符串的解析缓冲也随字段大小增长。单上传名额、接收上限及超时保持原有语义；本轮没有通过减小导入上限、取消校验或改动加密协议来降低内存。固定内存上限、分块认证加密和逐消息导入需要后续独立设计，不能将本轮测量外推到接近 2 GiB 的请求。
