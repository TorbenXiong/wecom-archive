# 架构

```text
本机企业微信数据
       │ 只读复制 DB/WAL/SHM
       ▼
source-windows → parser → MessageV1 / ClientExportV1
       │
       ├── 工作台本机采集 ───────────────┐
       │                                 │
       └── 专属采集端 → 可选脱敏 → 上传或离线加密导出 ┤
                                         ▼
                              校验 / 解密 / 幂等合并
                                         │
                                         ▼
                           SQLite/FTS5 / 媒体库 / 工作台
```

## 入口与运行模式

项目发布 `WeComArchive.exe` 工作台。工作台运行归档服务并打开管理界面；服务端按需生成携带签名绑定配置的采集端文件，采集端仍复用工作台的采集运行时。

采集宿主的公开入口集中在 `src-tauri/src/lib.rs`，通过重导出保留工作台使用的本机采集、密钥探针、采集端运行和升级 API。内部模块按职责组织：

| 模块 | 职责 |
| --- | --- |
| `commands.rs`、`state.rs` | WebView 白名单命令、响应类型、共享状态、任务锁与脱敏错误 |
| `collector_config.rs`、`collector_control.rs` | 绑定配置、签名校验、心跳同步与授权失效处理 |
| `collector_schedule.rs`、`collector_runtime.rs` | 采集计划、任务结果、窗口、托盘和进程生命周期 |
| `collector_transfer.rs`、`collector_http.rs`、`collector_incremental.rs` | 打包上传、HTTP 临时文件及增量检查点 |
| `paths.rs`、`source_keys.rs` | 数据与工作目录、源目录记忆、密钥验证及隔离探针 |
| `collection.rs` | 本机采集入口、只读快照读取及归档契约组装 |
| `source_directory.rs`、`source_messages.rs` | 会话、成员资料和消息内容投影 |
| `source_media.rs`、`source_protobuf.rs`、`source_sql.rs` | 媒体定位与校验、Protobuf 解码及源库字段适配 |

模块使用显式导入，内部类型保持 crate 内可见；底层 Windows API 继续由 `source-windows` 提供。`tests.rs` 保留原有测试及名称，真实环境验收的 `tests::authorized_real_*` 精确入口沿用；拆分不新增 commands、权限、网络入口或依赖，也不改变归档契约与采集策略。离线导出的文件写入单独封装，只有成功独占创建 `.partial` 后才取得清理权；创建失败保留已有文件，发布通过硬链接拒绝覆盖已完成文件。

React 只能调用白名单 Tauri commands。Windows API 和源数据适配集中在 `source-windows`；跨平台的 domain、parser、transfer、archive-store 和 export 不依赖 Windows API。

服务端入口保留公开桌面启动 API，内部按 `runtime`、`state`、`config`、`api`、`collector`、`service`、`auth` 和 `error` 拆分。HTTP 请求与响应类型集中在 `api/types.rs`，采集控制与本机调度分别位于 `collector/control.rs` 和 `collector/local.rs`。Windows 加密、DPAPI 和默认应用打开通过 `source-windows` 的 crate API 调用，不再通过路径包含其他 crate 的源码。

归档存储入口保留原有公开类型和方法，连接、迁移、schema、写入和修订分别位于独立模块，查询按消息、会话、参与人和统计拆分。参数化筛选谓词由消息查询和计数共用；正文与附件名搜索先确定候选消息，避免逐条重复执行 FTS。基准方法与测量边界见 [`benchmarks.md`](benchmarks.md)。

消息页搜索优先检查满足非文本筛选、按时间与稳定消息 ID 排序的一段记录：窗口按所需结果数的 32 倍增长，上限 4,096 条。正文包含匹配成功时，SQLite `CASE` 不再构造 FTS 和附件候选；正文不匹配时仍保留原有 FTS 分词及附件名语义。只有窗口内足以填满请求页时才采用结果，否则丢弃这次结果并执行完整候选查询；偏移与页大小之和超过 4,096 时直接使用完整路径。因此不截断稀疏命中或改变全量排序。附件候选先筛选媒体名，再解析引用，不新增索引、派生表或写入维护成本。计数和流式导出仍使用完整查询。

消息分页先按时间和稳定消息 ID 选择索引记录，再读取该页正文。已有 v2 归档在可写打开时以 `CREATE INDEX IF NOT EXISTS` 补建全局时间索引，首次打开需要额外时间与磁盘空间；数据库版本、字段和旧迁移 SQL 保持兼容。OFFSET 接口保留，深分页只跳过索引记录，仍随 offset 增长。

会话列表先按最近消息时间索引选定页，再读取统计与参与人信息。写入将会话最近消息时间合并为每批、每会话一次更新，保持原有字符串最大值及修订投影语义，减少排序索引的反复改写。`archive_conversation_stats` 缓存每个会话的消息数和去重附件数，`archive_conversation_media_refs` 记录会话内同一附件的引用次数；消息和附件关系的触发器在写入事务内维护统计，包括共享附件、修订替换、删除和会话投影迁移。旧库首次可写打开时在同一事务内回填这些内部派生表，后续打开不重复扫描。只读打开尚无派生表的 v2 归档时仍按原表计算，不修改归档。

FTS 保留原表及搜索语义，`archive_fts_rows` 单独索引消息 ID 与实际 FTS 行号；行号不依赖消息表行号，也不访问 FTS 的内部影子表。修订先按映射删除旧 FTS 行，再更新正文、插入新行并记录行号，全部处于批次事务内。旧版本写入会通过消息触发器使相关映射失效，新版本下次处理这些消息时以每批最多一次 FTS 扫描修复映射；正常新版本修订不再扫描整个 FTS。批次写入复用参数化 prepared statements，并将可写连接的语句缓存限制为 32 条，避免逐消息重新编译 SQL 及触发器程序。派生表和触发器均为 v2 的兼容附加结构，不改变四个版本化契约；代价是首次回填、额外磁盘空间和写入维护成本。

## 采集与传输

自动发现合并当前用户企业微信注册表设置、DPAPI 记住的目录和默认目录，统一去重排序，当前数据优先于历史 `Backup`。手动重试只扫描填写的本机子目录，成功后记住；采集端发现、本机采集和后台任务共用此逻辑。

源数据先复制到对应运行端的数据目录，再验证快照并解析，完成或失败后清理。工作台本机采集、快速导出和密钥探针快照使用 `serverData/work/<run-id>/`（配置 `WECOM_ARCHIVE_SERVER_DATA` 时跟随该目录）；采集端使用 exe 同级 `collectorData/work/<run-id>/`。工作台本机采集直接进入本机归档；服务端生成的采集端使用签名绑定配置和 DPAPI 保护的本地缓存上传。

服务端生成采集端时预置设备身份、令牌和目标配置，不要求用户输入服务端地址、注册码或密钥；服务端维护每个采集端的启停、采集选项和计划。控制响应使用 `CollectorControlEnvelopeV1`，包含修订号、15 分钟有效期和服务端签名；采集端只接受签名正确、未过期且不低于本地版本的配置。采集端在启动、任务前后及空闲心跳时轮询控制 API，配置缓存以原子文件保存，并在下一次任务前生效。上传包仍使用随机 AES-256-GCM 数据密钥，并以 RSA-OAEP-SHA256 封装。私钥仅以 DPAPI 保护形式保存在工作台。

工作台可维护多条固定间隔或每日定时本机计划，每个远程采集端维护一条目标计划。采集端启动时已启用计划，或收到从停用改为启用的配置后，立即采集并上传一次；任务锁忙碌时保留首次任务，普通周期无消息、目录或成员资料变化则跳过上传。调度器与进程同生共灭，采集和上传共用任务锁。本机计划在内部配置中单独保存成功任务的开始时间，下次从该时间前移 5 分钟增量读取，失败不推进游标；升级后的旧配置没有此游标时先全量扫描一次，回补可能遗漏的数据。尝试时间与成功时间分别记录：远程管理页只用成功上传时间展示“最近成功”，本机计划仍使用成功完成时间。

远程计划的增量状态由 `collector_incremental` 管理，保存在 `collectorData/instances/<collectorId>/collection-progress-<源标识哈希>.db`；兼容旧版无 UUID 身份时使用身份哈希目录。该本地辅助库只保存标识哈希、内容指纹、时间与计数，不保存聊天正文、人员资料、路径或凭据。状态按采集端和数据源隔离；目标地址、身份、密钥、采集范围、脱敏策略或程序版本变化时重新全量核对，普通计划时间和心跳修订号变化不使进度失效。首次扫描无游标；后续从上次成功扫描开始时间前移 5 分钟读取。无变化时也提交扫描进度，但保留原成功上传时间。上传失败不推进；上传成功后用单个 SQLite 事务保存指纹和检查点，保存失败允许服务端幂等重放。每隔 24 小时在下一次计划任务中全量核对，补充窗口外的迟到记录、旧消息撤回、转写和附件变化；系统时钟回退也触发全量核对。

消息去重指纹忽略采集批次 ID；目录和成员资料分别比较，避免增量窗口移动导致资料载体变化被误判为消息修订。脱敏先额外读取 10 分钟上下文并处理完整窗口，再移除上下文记录与未变化消息；成员资料移到窗口内的消息携带。上传重新计算批次和导出校验和，仅携带所选消息引用的附件字节，复用原 `ClientExportV1` 和加密包协议。增量读取只从快照查询历史会话标识以维持员工身份与消息方向，不解析旧消息正文。开启离线导出时仍全量读取并保留完整本地结果；采集端手动采集和管理员立即采集也保留原全量读取行为。数据库快照、媒体索引和单包加密尚未流式增量化。

采集端身份由 `collectorId` 和访问令牌确定，心跳不会因来源 IP 相同而删除其他采集端；重新生成后的旧身份由管理员显式撤销。断网、超时和服务端临时错误保留采集端进程，由下一轮心跳重试；只有 HTTP 401 且本产品返回 `UNAUTHORIZED` 时才停止运行。上传和心跳的令牌经匿名管道交给系统 curl，不出现在命令行或临时文件中；请求正文暂存于采集端 work 目录并在请求结束后清理。

工作台在创建窗口前，按本进程服务端页面的精确 origin（含端口）添加运行时 capability，仅授予主窗口退出、检查更新和安装更新三个 commands；局域网和自定义端口不需要扩大静态 URL 白名单。

导出支持独立选择会话时间和会话内容时间的升序/降序：会话时间取会话内最近消息时间，内容时间取单条消息时间。会话工作台的消息顺序由服务端在全量数据上排序后再分页，避免仅反转当前页造成跨页顺序错误。

服务端依次限制请求体、校验身份、验证包与归档契约、解密、持久化媒体、按源消息 ID 幂等合并并记录审计。工作台逐文件校验并原子写入内容寻址媒体库。SQLite 使用 busy timeout 处理并发与异常退出后的短暂锁定；重复消息保持不变，内容变化形成修订。

JSON 和加密包上传在认证后、开始读取请求体前共用一个导入名额，其他上传异步等待，避免多份大包同时驻留内存。等待名额最多 60 秒，超时返回 HTTP 503 / `IMPORT_BUSY`；接收期间连续 60 秒没有非空数据或接收超过 30 分钟，返回 HTTP 408 / `IMPORT_RECEIVE_TIMEOUT`，清理本次临时文件并释放名额。这些时限不取消已经开始的解密或归档事务。读取临时文件、解密、契约校验和归档写入统一在阻塞线程执行；即使调用方停止等待，阻塞任务仍持有名额直到处理结束。接收取消或解析失败时清理本次临时文件。加密包仍整体解析，单包峰值内存尚未实现有界流式处理；本机采集继续使用独立的采集任务锁。

大包路径保留原有序列化与校验字节：摘要直接接收 serde JSON 输出，不构造完整校验缓冲。包编码按块格式化十六进制密文，预留最终输出大小；原明文在生成密文后释放。服务端从文件缓冲借用未转义的十六进制字段，只解码一次并精确分配二进制空间，文件缓冲在解密前释放；不使用可能保留超大字符串 scratch 的 reader 路径。JSON 导入直接构造契约对象并递归兼容原时间格式，额外阅读视图由解析器跳过。媒体按 64 KiB 解码、哈希和写入 `.partial`，验证完成后才原子发布；失败清理本次拥有的临时文件，重复附件仍验证传入内容。归档阶段逐附件、逐批次释放；采集端缓存用不可变共享引用复用，脱敏时按需复制并流式重算校验。以上优化不改变归档契约或加密算法，仍保留完整密文、完整明文及完整契约对象的单包阶段，不能据此宣称总内存有固定上限。方法和测量见 [大包内存基准](package-memory.md)。

服务端配置、访问令牌和采集端 DPAPI 配置先写入同目录独占临时文件、刷盘，再覆盖重命名，不先删除原文件。服务端主配置保存前保留上一版可解析配置 `.bak`；损坏，或存在副本、旧临时文件、采集端目录但主配置缺失时停止启动。旧版纯本机归档可能尚未持久化默认企业配置，仅有归档不视为配置丢失。已有归档缺失访问令牌时停止启动。备份范围与恢复边界见 [备份与恢复](backup-recovery.md)。

设置、计划和采集端控制在同一个配置锁内构造候选配置，完成校验、响应签名和持久化后再替换运行时配置；保存失败保留原内存状态，日志级别也不提前切换。本机计划结果和上传成功时间写入失败时保留原游标与状态并记录脱敏错误，归档成功结果仍有效。访问令牌的认证、文件保存与内存哈希切换由同一个锁串行执行；并发请求在获得锁后重新校验当前令牌，避免旧令牌继续覆盖新的认证状态。

升级分为工作台和采集端两条路径。工作台手动读取 GitHub/GitLab Release API，只接受 HTTPS、严格的 `x.y.z` 版本、对应 Windows x64 EXE 和 SHA-256 校验值；优先使用 GitHub 资产 digest，缺少 digest 的服务使用同名 `.sha256` 附件。下载后由独立替换助手等待父进程退出，保留旧文件并在新进程未完成启动时回退。采集端升级请求由服务端管理员创建，服务端通过已认证心跳返回签名的 `software-update.v1` 描述；采集端从同一服务端下载当前 EXE，追加现有绑定配置后再走同一替换助手。升级路径不复用归档契约，不暴露令牌到日志。

## 浏览与导出

工作台将会话、参与人、消息、引用和群信息投影到界面。全局搜索结果可定位到原消息；分页后回到顶部，滚动时可跳到顶部或底部。媒体按内容哈希存储，图片通过已认证 API 预览，文件映射为带安全扩展名的本机副本后由 Windows 默认应用打开。归档修订变化后，页面自动重新读取当前会话。

会话目录首先只读取 50 条，接近列表底部或点击“加载更多会话”时继续读取；重复滚动共用在途请求，失败后保留原偏移重试。搜索筛选和多选导出也能手动加载后续会话。归档更新时重置分页并丢弃旧在途响应，同时保留当前选中会话；目录不再自动读取全部页面，但尚未使用列表虚拟化。

工作台按当前会话、当前筛选或全部档案导出单个 JSON、CSV、HTML 或 Markdown 文件。阅读型 JSON、HTML 和 Markdown 以会话为分组，CSV 保持同一会话连续并带会话字段；本机和服务端完整 JSON 均保留既有可导入契约，同时附加会话消息视图。服务端完整 JSON 以本次批次 `.partial` 流暂存消息，再流式计算契约校验和写出阅读视图及批次，保留原批次授权证据、保留策略、成员目录和时间精度；成功、失败和取消均清理本次暂存文件。服务端仍只导出媒体元数据和引用，不额外嵌入媒体字节。导出使用 `.partial` 原子完成并拒绝覆盖已有文件；CSV 防公式注入，HTML 全量转义并禁止脚本和远程资源，Markdown 对结构字符及 HTML 标签进行转义。

归档导出由 `ArchiveExportSource` 和 `archive-export::export_streamed` 连接：在同一个 SQLite 只读快照中先扫描筛选结果、保留会话与参与人元数据，再按筛选后各会话的最近消息时间排序，逐条读取、脱敏并写入文件。简化模式移除公告和看板后重新计算会话时间，附件缺失统计与实际输出核对。脱敏保留相邻消息上下文，隐藏的公告仍能提供上下文；降序输出仅缓冲相邻原消息。旧修订造成正文与索引字段不一致时，仅对受影响会话按正文排序记录键，再逐条读取正文，保持原筛选和输出语义。内存随会话数、参与人数及单条消息大小增长，不再保留完整消息集合。长时间读取会延后 WAL 回收；导出串行执行，避免多个导出同时保留快照。直接采集的本机完整 JSON 仍使用既有可导入契约和采集结果集合；本机阅读型 JSON 的序列化也不再构造完整 JSON 中间对象。

## 版本化契约

`MessageV1`、`ArchiveBatchV1`、`ClientExportV1` 和 `UploadEnvelopeV1` 保持字段语义兼容。采集传输继续使用 `enterprise-package.v1` 作为既有协议版本名，解密后进入 `ClientExportV1` 校验链路；该内部名称不代表独立产品版本。
