# 归档性能基准

基准程序只使用确定性的合成消息，调用现有 `ArchiveStore` 和 `archive-export` API。它不会发现或读取企业微信目录，也不会发送网络请求。构建使用本地缓存、`--locked --offline`，没有新增第三方依赖。

## 运行

在仓库根目录使用 PowerShell：

```powershell
./scripts/benchmark-archive.ps1
```

默认分别运行 10 万、50 万、100 万消息，每个规模独立启动一个进程。小规模检查可使用：

```powershell
./scripts/benchmark-archive.ps1 -Counts 1000 -QuerySamples 1
```

格式测量使用完整模式、紧凑排版、会话和消息升序，不启用脱敏；脱敏与排版选项的内容一致性由回归测试验证，其吞吐量未在这组数据中测量。

`-BodyBytes` 调整合成正文长度，默认 256 字节；`-QuerySamples` 调整预热后的重复查询次数，默认 5。`-Cargo` 可指定已有 Cargo 可执行文件，脚本也会查找当前用户已有的 `.cargo/bin/cargo.exe`。所有构建均为 Release，沿用项目发布配置。

当前默认 `-ExportMode Stream`，调用服务端实际使用的快照与流式导出实现。使用 `-ExportMode Legacy` 可测量当前代码中保留完整消息集合的对照路径；它已经包含本轮索引和逐条 JSON 序列化改进，不等同于下面记录的历史实现。新报告为 `archive-benchmark.v2`，包含 `export_mode`。

报告位于 `target/benchmarks/report-<随机 ID>/<消息数>.json`，仅包含规模、耗时、文件大小和进程峰值工作集。报告先写入 `.partial` 再完成，不覆盖已有报告。数据库和导出文件在本轮独立工作目录内生成，成功后自动清理；被强制终止或进程崩溃的运行可能留下合成数据工作目录。`target/` 已被 Git 忽略。

## 数据与校验

- 按每批 2,000 条写入；一半消息集中在同一大群，其余分布到 1,000 个群。
- 100 个合成发送人；每三个消息共享同一时间，验证相同时间下的稳定排序。
- 每 20 条消息有一个缺失附件引用，仅使用合成文件名，不生成附件内容。
- 每 10,000 条消息包含搜索标记，正文同时含中文、英文和重复填充文本。
- 初始写入之后重放一个批次；再写入含 100 条修订的重叠批次，并新增 1,000 条消息。
- 校验插入、重放、修订和最终计数，查询结果长度与顺序，以及导出消息、缺失媒体计数和 `.partial` 清理。

## 指标解释

| 指标 | 测量范围 |
| --- | --- |
| 初始写入 | `ingest_batch` 调用累计耗时；另记包含夹具生成的总耗时 |
| 增量写入 | 批次重放、重叠修订和新增消息分别计时 |
| 会话列表 | 最近 100 个会话及其统计信息 |
| 分页 | 全局与大群首屏，以及约 80% 位置的深分页，每页 100 条 |
| 搜索 | FTS 标记查询及匹配数统计，包含附件名搜索逻辑 |
| 时间范围 | 指定时间窗口内的前 100 条 |
| 导出准备 | Stream 为筛选结果扫描、统计和会话/参与人元数据准备；Legacy 为每页 50,000 条加载完整数据集并排序 |
| 格式导出 | 完整、紧凑 JSON、Markdown 和 CSV；Stream 另包含从数据库逐条读取，二者均包含写入、原子完成及文件哈希 |
| 数据库大小 | 关闭最后一个连接后的主数据库大小 |
| 峰值内存 | Windows 记录的进程峰值工作集，包含夹具、查询和全部导出阶段 |

查询记录首次耗时、重复运行的中位数和 P95。首次运行不等同于磁盘冷缓存；5 次重复的 P95 接近最大值。这是定位瓶颈的开发基准，结果受磁盘缓存、后台任务和内存压力影响，不能直接作为生产 SLA。它没有覆盖真实源数据库解密、媒体字节传输、HTTP 上传、前端渲染或多客户端并发。

## 第一轮结果（2026-10-10）

旧查询在 10 万条数据下，大群消息首屏中位耗时约 817 ms，FTS 搜索约 8,602 ms，搜索计数约 7,626 ms。50 万条旧查询运行在 FTS 阶段已消耗约 20 分钟 CPU，因此主动中止，没有将它报告为完成。

执行计划显示，可选条件 `(? IS NULL OR column = ?)` 使会话查询扫描消息表并临时排序；相关 FTS 子查询对每条消息重复执行搜索。改写后，只为实际筛选条件构造参数化谓词，并通过 FTS 和附件名搜索的候选 ID 集合查询消息。同一条消息同时匹配正文和附件名时只返回一次。

10 万条数据下，大群消息首屏中位耗时约 0.53 ms，FTS 搜索约 13.72 ms，搜索计数约 13.34 ms。正文和附件搜索、组合筛选、分页计数与同时间排序已补充回归测试。数据库版本和版本化契约未改变。

## 第二轮实现（2026-10-11）

可写打开归档时补建兼容的全局时间索引，分页先选定页内记录再读取正文。数据库仍为 v2；既有归档首次补建索引需要额外时间和磁盘空间，本基准使用新建数据库，未测量旧归档首次补建索引耗时。

归档导出使用同一只读快照保留统计和元数据，逐会话、逐消息读取并写入，不再保留全部消息。阅读型 JSON 逐条序列化，完整模式单次最多构造一条消息的 JSON 值。直接采集的本机完整 JSON 仍保留可导入契约和原采集集合。内存随会话/参与人数及单条消息大小增长；长时间快照会延后 WAL 回收。

回归覆盖四种格式及简化、排版、独立排序组合的文件内容一致性，组合筛选、重复会话 ID 去重、跨消息上下文脱敏（含隐藏公告和降序输出）、读取快照一致性、旧修订正文/索引字段不一致和纳秒排序、取消/失败清理、统计不一致拒绝发布，以及目标文件和 `.partial` 文件的并发保护。

## 第三轮实现（2026-10-11）

会话列表先选页，再读取增量统计：消息数按会话维护，附件数由会话内附件引用次数维护，多个消息或多个 ordinal 引用同一附件只计一次。原始表仍为统计依据，内部派生表由事务触发器维护，正常读取不重新遍历会话内全部消息。会话最近消息时间按批合并更新，保留原有字符串最大值及旧修订投影语义，减少会话排序索引的写入次数。

FTS 消息 ID 仍保持原有 `UNINDEXED` 字段，另建索引表记录实际 FTS 行号。正常修订按行号删除旧条目，保留原搜索结构和语义；批次写入复用参数化 prepared statements，最多缓存 32 条，避免反复编译写入语句及触发器程序。原数据库版本 v2、旧迁移 SQL、版本化契约和 0.0.8 版本保持兼容，没有新增依赖或改动锁文件。

旧归档首次可写打开时在一个事务内回填统计、附件引用次数及 FTS 行号，后续打开不重复回填。旧版本的消息正文更新会使相应行号映射失效，新版本下次处理该批消息时以最多一次 FTS 扫描修复映射。只读打开没有统计表的旧 v2 归档仍使用原表计算。首次旧库回填、旧版本写入后的修复扫描、会话投影移动和共享附件密集场景的吞吐未在本组基准计时；这些路径由兼容与一致性测试覆盖。

本轮基准另校验生成数据对应的会话消息数、去重附件数，以及修订正文的搜索计数。最终报告增加 `storage_accelerators: statistics-and-fts-rowids.batched.v1` 标记；下面仅使用最终实现的完整 Release 测量，中间版本结果不计入对照。
