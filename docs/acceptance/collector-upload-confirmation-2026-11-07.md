范围为 `feature/collector-upload-confirmation`，基于 `75c159e`。本轮完善已绑定远程采集端的上传结果确认及超时协调，保留既有上传接口、版本化归档契约、数据库结构、依赖与锁文件。上述验证执行时未提交、推送、发布或生成交付包。

## 行为修正

- 服务端新增独立设备上传记录及查询接口，以认证设备和上传 UUID 隔离，使用独立容量，不占工作台任务记录额度。文件完整接收并同步后才返回 202，归档结果另行查询。
- 上传请求绑定导出 UUID 和实际明文摘要，服务端在归档写入前校验包内外身份与完整性；采集端也核对最终结果的协议、上传 UUID、导出 UUID、摘要、完成时间和计数。
- 上传前明确失败清除本次待确认标识；可能已发出或响应丢失时仅查询原 UUID。结果未知不作为成功返回，不推进该次增量进度，也不自动重 POST。
- 手动继续确认成功后直接返回原上传结果，不读取或重传旧的本地快照；定时任务先确认旧上传，再按持久化的旧检查点保守扫描。
- 本地采集成功、配置错误及其他失败不会隐藏尚存的待确认上传。远程成功一经确认就记录其时间和本次条数，后续本地扫描或检查点写入失败不会抹去该事实；累计指纹数量不会用本次条数替代。
- 手动采集和上传由后台工作线程持有运行锁及完成状态，命令等待取消不会提前放锁；线程异常且存在待确认上传时，命令返回结果未知。
- 界面显示上传阶段、待确认状态和继续确认入口；“最近上传”使用已证实的本次消息数量，避免首次上传续查成功后误显示零条。

接口、预算、容量和恢复限制见 [采集端上传结果确认](../collector-upload-confirmation.md)。

## 验证中发现的情况

全量并发时，新增 HTTP 测试夹具曾因 accepted socket 继承非阻塞模式而出现 Windows `WouldBlock`。现已显式切回阻塞模式，并保留有界 accept/read、补齐 write timeout；未串行化测试或放宽断言，最终全工作区通过。

一轮服务端全量检查中，原有导出标识测试的 5 秒等待发生超时。其单独复跑通过（0.65 秒），与 8 次 JSON 导出用例的最小并发组合也通过（2 项总计 6.84 秒），最终默认参数全工作区通过。现有全局 `EXPORT_FILE_LOCK` 会在独立目录间竞争，批量导出还会持锁等待秒级文件名避重；证据支持排队负载造成偶发超时，未发现任务丢失。未调整该测试超时、断言或生产导出锁，此并发风险留作后续优化。

- 全部新增验证使用合成数据、实际 handler 和本机 TCP/curl。未读取真实企业微信源、重跑真实备份恢复或 NTFS 写满、触发 UAC，亦未执行真实远程网络、原生 WebView2 或 Release EXE 验收。
